# AI Coach — Epic 3A

Coach is private, advisory and optional. AI advice is not SRS scheduling. AI supplementary exercise is not LearningAttempt. AI intervention does not change mastery.

## Public API (through Identity)

All routes start `/api/learning`; authentication and ownership derive from existing Identity middleware, never request user IDs. Foreign session/intervention returns 404; anonymous 401.

- POST `/sessions/{id}/coach-analysis`, body `{language: "en"|"ru"}`; GET same route. POST initiates a separate bounded provider call after session completion, outside learning transaction. One durable analysis per session/prompt version; completed cached, pending reused, failed controlled retry. GET missing returns 404. POST/GET returns CoachAnalysisDto below, including Failed status for noncritical typed provider failures.
- GET `/interventions/{id}` -> CoachInterventionDto.
- POST `/interventions/{id}/accept`, `/dismiss`, `/complete` (empty body) -> CoachInterventionDto. Complete applies to lessons only; practice completes after all exercises answered.
- POST `/interventions/{id}/exercises/{exerciseId}/answer`, body `{optionId: string, responseTimeMs?: number}` -> `{exerciseId, correct, explanation, intervention: CoachInterventionDto}`. Repeated same answer returns stored result; changed answer conflicts. No solution in public DTO before submission.

Analysis DTO: `{id, sessionId, status: Pending|Completed|Failed|Disabled, decision: None|Intervention, summary, failureCode?: string|null, provider, model, promptVersion, schemaVersion, createdAt, observations: ObservationDto[], interventions: CoachInterventionDto[]}`.
Observation DTO: `{cardId, learningRevision, type, evidenceSummary, explanation}`. Allowed types RepeatedFailure, SlowRecall, LowMastery, RecentRegression, RepeatedHard, WeakAfterMultipleAttempts. Internal references validated against passed current-revision attempt IDs; public UUID evidence not required.
Intervention DTO: `{id, analysisId, cardId, learningRevision, type: Explanation|MicroLesson|ExtraPractice, title, status: Suggested|Accepted|Completed|Dismissed|Stale|Unavailable, createdAt, startedAt?, completedAt?, lesson?: {explanation, examples: {source,target}[], tips: string[]}, exercises: {id, type: RecognitionChoice, prompt, options: {id,text}[], answered: boolean, correct?: boolean|null}[], evaluation: {status: Unknown|NoFollowUpEvidence|FollowUpSuccess|FollowUpFailure, postInterventionAttempts: number, firstPostInterventionOutcome?: string|null, firstPostInterventionReviewedAt?: string|null}}`.

## Internal read model and provider

Versioned explicit allowlist context: completed session summary, at most 5 problematic session cards, current content (bounded words/strings), current deterministic learner state, latest at most 6 current-revision attempts per card at or before session completion; historical revision counts separately. No email/identity/user IDs/social/tokens/config. Revision-mismatched session evidence never attributed to current words. Language UI en/ru. Context limits in one class/config. Empty/insufficient context returns None without paid call. Provider may also return None.

Structured result: decision, summary, observations [{cardId, learningRevision, type, evidenceAttemptIds, evidenceSummary, explanation}], interventions [{cardId, learningRevision, type, title, lesson?, exercises:[{type:RecognitionChoice,prompt,options:[{id,text}],correctOptionId,explanation}]}]. IDs for interventions/exercises generated by server. Strict enums, references, duplicates, number and length bounds, nonempty required content, option IDs/answer consistency, current revision and grounded observation type checked before any intervention insert. Reject invalid result atomically. No provider prose accepted. No raw output retained/logged.

Prompt v1 treats content as untrusted DATA. Only known outcomes/timing/history can ground claims; exact wrong answers/confusion pairs are unknown. Prefer None to unsupported advice. Never change scheduling, mastery, ownership, content or normal history. Lessons/exercises remain short plain structured text; Angular interpolation only.

Implemented limits: cards 5, recent attempts/card 6, observations 5, interventions 3, exercises/intervention 4, options 2–4, examples 3, tips 3, prompt characters 24000, provider output characters 16000, title 120, prose fields 800, short fields 240.

## Persistence and safety

Analysis holds session/collection FKs, status/decision, validated observation grounding, provider/model/prompt/schema provenance, first-request language and retry metadata. Context and raw provider responses are not retained. Intervention holds analysis FK, card/revision, structured lesson/private exercise payload and durable lifecycle. Separate InterventionAttempt holds exercise/card/result/time; unique exercise answer per intervention. Server serializes concurrent analysis/lifecycle operations with database locks and unique constraints; never holds learning transaction across LLM latency. Pending recovery bounded by lease/timeout. Card edit/reset makes previous-revision work Stale; deleted card/collection unavailable. Future ordinary current-revision attempts after intervention completion produce diagnostic follow-up metrics only; no causal effectiveness claim.

OpenRouter uses existing AI configuration/typed errors/HTTP conventions; separate Coach provider because card extraction contract is domain-specific. Fake provider is deterministic for tests/local acceptance. Disabled/missing key never breaks learning.


## Actual implementation and temporal semantics

The provider context intentionally excludes session/collection database IDs: only opaque card/attempt correlation IDs needed for validation remain. `CoachSessionContext` contains schemaVersion, language, completedAt, summary, revisionMismatchCards, contentOmittedCards and cards. Each candidate has bounded current words/translations, current learner state including source/model version, current/historical revision evidence counts, recent attempts and session attempt. Transcription is omitted as unnecessary for this slice.

Context reads use a PostgreSQL repeatable-read snapshot. Only actual session members with matching current revision, at least two current-revision attempts at/before completion, and an Again/Hard or >=15000ms session review qualify. The provider may still choose None. At most four words per card, 240 characters each; larger/empty cards are omitted rather than truncated. State is explicitly current at analysis time; bounded attempts stop at session completion. If the rebuildable cache is absent, the bounded reconstruction is marked `BoundedObserved`, with exact total evidence count separately reported. This is not a full aggregate rebuild and is never saved into learner state.

The output validator rejects unknown JSON members and missing required structured fields, exact enum mismatches, unknown revisions/cards/attempts, repeated observation card IDs, duplicate card/type interventions, invalid options/solutions, nulls, control characters and size violations. Machine grounding gates: RepeatedFailure >=2 referenced Again; RepeatedHard >=2 referenced Hard; SlowRecall >=2 referenced durations >=15000ms; LowMastery current score <.4 with >=2 observations; WeakAfterMultipleAttempts current Weak with >=2 observations; RecentRegression referenced success preceding referenced Again. Recognition prompt must exactly match a supplied source value and its correct option that same source's supplied translation. Generated exercise/intervention IDs are assigned by the backend. Semantic quality of prose/examples/distractors remains a provider limitation.

`CoachLimits` centralizes limits. Prompt `coach-v5`, schema 1, provider maximum 3000 output tokens, timeout clamped 1–90 seconds and total service timeout 90 seconds. Request JSON including schema/system text is capped at 24000 characters; output content 16000, HTTP response envelope 128000 bytes. Lists/prose limits above are validated independently of token settings.

## Durable lifecycle and concurrent requests

Migration `20261029000000_AddAiCoach` adds `words.CoachAnalyses`, `words.CoachInterventions`, `words.InterventionAttempts`. Validated observations include grounding IDs in internal text JSON. Immutable lesson/private exercise structure uses internal JSON; lifecycle and evaluation keys remain indexed columns. Separate exercise table is unnecessary for this slice. Public DTO explicitly maps only safe exercise fields; correct option IDs and submitted option IDs never serialize to clients. Answer response reveals only correct flag and explanation after submission.

Analysis claims serialize on the session row; unique `(SessionId, PromptVersion)` prevents duplicate records. Completed analysis is reused independent of later language/model changes. Failed generation has a 5-second cooldown and at most three retries after the initial attempt. Pending has a 120-second lease; a later POST can recover an expired lease. Generation number fences obsolete workers. No scheduler/background recovery job: retry requires a new request. GET is read-only. No database transaction remains open during provider latency. Final result rechecks revisions under card locks; all validated interventions commit atomically or analysis fails. Lifecycle/answers serialize on intervention then card; duplicate same answer plus responseTimeMs replays, changed input conflicts.

Suggested -> Accepted -> Completed, or Suggested/Accepted -> Dismissed. Accept and lesson completion are idempotent; practice completion is automatic after every unique exercise is answered. Lesson `/complete` cannot complete practice. Edit/reset makes unfinished older work Stale and hides payload; already completed work remains historical Completed with payload hidden. Deleted card maps to Unavailable with title/payload hidden. Deleted collections block analysis and intervention reads. These are derived availability statuses rather than destructive rewrites of historical lifecycle rows. Follow-up evaluation is Unknown before completion/when revision no longer matches, NoFollowUpEvidence until future normal evidence, then first outcome Again -> FollowUpFailure, other outcomes -> FollowUpSuccess. Hard is a successful review under existing scheduler vocabulary. This is a descriptive diagnostic, not proof of causation.

## Provider, configuration and privacy

`IAiCoachProvider` remains separate from domain-specific `IAiCardGenerationProvider`. Coach reuses `AiCardGeneration` provider choice and `OpenRouterOptions` credentials/model/URL/timeout, existing HttpClient DI and typed `UpstreamServiceException` conventions. No broad extraction/refactor of existing card generation. Coach reads streamed HTTP responses under explicit limits, maps 429/configuration/unavailable/invalid output and stores sanitized failure codes. Missing OpenRouter credentials fail rather than silently inventing advice. `Fake` is deterministic local/test behavior with short pair recall lesson and two recognition questions; it is not an LLM quality demonstration. `AiCoach:Enabled` / Docker `LW_AI_COACH_ENABLED` controls analysis and automatic surfacing. Disabled POST/GET returns an ephemeral Disabled DTO, hides cached advice and neither invokes the provider nor changes durable records. Reenable reuses completed cache; existing private intervention APIs remain available for historical explicit work.

No account PII, ownership IDs, JWTs, auth headers, configuration/secrets, social data or unrelated collection content enters the model context. Arbitrary user-written card text can itself contain PII; allowlisting cannot remove that fact. The feature transmits selected private learning content/evidence to configured provider when enabled. Raw output/context are not retained or logged; validated private advice, source references and attempts survive soft deletion under existing retention policy. No new hard-purge/account-erasure policy is claimed. Card content is DATA in the versioned system prompt, never authority to alter instructions or schema. Structured parsing and grounding protect machine behavior; generated teaching prose is still advisory.

## Frontend and limitations

Standalone Coach component mounts only after durable adaptive session completion. Normal deterministic summary remains visible during a separate analyze request. Pending polls every 2s at most 15 times, cancellable on navigation/session changes; None/Disabled hides the entire block. Noncritical failures show localized retry. Acceptance/dismissal is explicit. Lessons and examples use interpolation; no HTML/Markdown rendering. Recognition choices call only Coach answer endpoints, with stable payload retry and keyboard-focus feedback. EN/RU interface; first generation language remains cached for that session/version. Existing legacy due-only review has no durable session and does not invoke Coach.

No browser session/intervention history/resume navigation is added; reload follows existing Epic 2 session behavior. Durable APIs retain work for future history UX. Limits and candidate thresholds are conservative product heuristics. Live paid LLM quality, extreme collection load, production deployment and causal effectiveness are outside local acceptance. Future ordinary attempts are the only source of follow-up recall diagnostics.


## Prompt v2 clarification (2026-10-29)

Repeated current-revision Again/Hard outcomes can justify an optional meaning recap or practice without exact wrong-answer evidence. Missing choices forbid invented confusion/psychological explanations, not all intervention. Two Again plus one Hard on Weak is an explicit eligible example, not a mandatory intervention rule. None remains valid where no useful grounded action exists. Summary should be brief, human-facing and omit numerical mastery/internal labels/cognitive diagnoses. `coach-v2` has a new session/prompt cache key: existing v1 analyses remain historical; a new explicit analyze request can produce v2 once and then reuse it. No automatic historical regeneration or paid batch reanalysis.


See [private read-only Coach diagnostics](coach-diagnostics.md) for captured metadata, legacy reconstruction and JSON download.

### coach-v3 contract and routing

RecognitionChoice `prompt` must exactly equal one supplied `currentContent.value`, including its original spelling. For value `eventually`, output `eventually`, rather than a question such as `What does eventually mean?`. Its correct option must match the translation paired with that same value (existing trimmed case-insensitive answer comparison remains). An explanation or micro-lesson has a lesson and no exercises; extra practice has exercises and a null lesson. Evidence IDs and observation gates still apply; None is still permitted. The schema describes these constraints and mirrors compatible existing text/list bounds.

Only the Coach OpenRouter request adds `provider.require_parameters=true` to require support for the requested structured output. The model, 3000-token budget, reasoning and card-generation request remain unchanged. v3 creates a new cache entry only on explicit analyze; v1/v2 results remain historical. Failure diagnostics expose safe rule codes/known JSON paths; see [diagnostic contract](coach-diagnostics.md).

Coach response observability preserves the existing string provider API while adding per-call immutable content+diagnostics results for the service. OpenRouter response finish/usage metadata and safe output-boundary flags survive both success and validation failure. JSON failures retain zero-based numeric parser coordinates only. These are diagnostic additions with unchanged coach-v3 prompt, schema1, validation and generation settings; see [diagnostics](coach-diagnostics.md).

### Automated behavior evaluation

A standalone synthetic-context evaluation harness checks the current production Coach provider/prompt/schema with the production output validator. It scores contract validity separately from benchmark behavior: successful-review and isolated-error controls should abstain; repeated-current-revision Again cases should offer grounded assistance. A structurally valid None on a repeated-failure benchmark is `missed_help`, not a successful evaluation. These are regression expectations for the benchmark, not a change to the production API's valid None semantics.

The harness requires no learner sessions, browser, database data export or manual answer grading. Default Fake mode verifies the harness offline; it is explicitly not evidence of Gemma quality. Explicit live mode uses an environment-only test API key, bounded repeats/model count/call count and sanitized per-case/aggregate JSON results. Ordinary CI/unit tests do not call paid providers. This measures abstention, evidence grounding and existing structural/content rules, not full linguistic or pedagogical quality. See [automated evaluation instructions](../docs/coach-evaluation.md).


### coach-v4 intervention alternatives

The outgoing strict JSON Schema uses two intervention alternatives selected by `type`: Explanation/MicroLesson require a non-null lesson and an empty exercises array (`maxItems:0`); ExtraPractice requires `lesson:null` and1..4 recognition exercises. Every branch retains the same required DTO fields, additionalProperties:false, bounds and grounded-answer rules. If both lesson and practice help, emit separate bounded interventions for the same card. The local structural validator selects only the known type branch, supports explicit null, and preserves safe lesson/practice diagnostics. No response repair or weaker acceptance is introduced.

At most one observation may reference each cardId. The prompt and schema descriptions explicitly require choosing one supported type and combining supported reasons in that observation. Property-level uniqueness across array items remains a semantic validator check; uniqueItems alone would not enforce it. Duplicate-card observations still fail observation_duplicate_card.

The changed prompt/schema request uses cache prompt version coach-v4, while public provider result DTO/schemaVersion remains1. Existing v3 rows remain historical; explicit new analysis under v4 uses a new cache entry, no automatic regeneration. Gemma, card generator,3000-token budget, reasoning settings and valid None behavior are unchanged. Run the same automated evaluation command with `--output gemma-v4.json` to compare to the v3 baseline. Local stub/unit success does not establish improved real-model behavior; provider structured-output enforcement varies by endpoint.

Evaluation-only reasoning control: the standalone runner can request an explicit reasoning effort for controlled experiments, while production Coach/provider defaults and card generation remain unchanged. Keep max_tokens3000, prompt/schema/fixtures and timeout fixed when comparing default effort to low. The report records requested effort, not a claim that an upstream endpoint applied it. GLM's mandatory thinking is not disabled; the test requests a lower effort. See evaluation instructions for opt-in flags and safe reports.


### coach-v5 required text

Required text schemas now include minLength:1 alongside existing maxima: observation evidenceSummary/explanation, intervention title, lesson explanation/example source/target/tips entries, recognition prompt, option IDs/text, correctOptionId and evidence ID strings. Empty examples/tips arrays remain valid. Root summary explicitly allows empty text for None; exercise explanation remains optionally empty as in the existing validator. Intervention summary is still required to be meaningful by prompt and semantic validation. No generated fallback prose or output repair.

The prompt/descriptions explicitly require brief nonblank mandatory rationale. Local structural validation enforces minima using existing text_empty code and safe field paths; semantic whitespace/control/grounding checks remain. minLength:1 only rejects zero-length strings, not whitespace-only strings. Prompt/cache version is coach-v5, result DTO/schemaVersion remains1; historical v4 analyses remain untouched with no automatic replay. Model, card generator, token/reasoning settings, limits and valid None behavior are unchanged.
